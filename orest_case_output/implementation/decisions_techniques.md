# Adaptations techniques d’implémentation

Les définitions métier D01–D30 restent inchangées.

1. **Projection explicite des alias.** Les projections qualifiées utilisent systématiquement `AS nom_colonne`. L’adaptateur 1.10.1 comparait autrement des noms qualifiés lors de la vérification incrémentale. Aucun `full-refresh`, suppression de table ou effacement d’historique n’a servi à résoudre ce problème. Le script de migration préventif n’a renommé aucune colonne physique : les noms réels étaient déjà corrects.
2. **Contrôle de contenu et anti-jointure en une évaluation.** Une `LEFT JOIN` filtrée sur la clé de run et la clé de grain remplace l’évaluation double du candidat. Pour une clé absente, insertion ; pour une clé identique, aucune insertion ; pour un `row_hash` divergent, `throwIf` bloque. Il s’agit de la même anti-jointure logique, avec contrôle de divergence sur les correspondances. Les fixtures de reprise et de divergence vérifient ce comportement.
3. **Sérialisation des tuples.** `toJSONString(materialize(tuple(...)))` conserve la préimage typée prescrite. La matérialisation explicite, les blocs limités et un seul thread réduisent la pression mémoire sur le serveur local. Des rejets mémoire transitoires ont également affecté une simple lecture de comptage ; ils sont consignés, et les lectures seules peuvent être rejouées. Une insertion dbt interrompue ne vaut jamais succès : les métadonnées restent figées et les clés/empreintes sont réconciliées.
4. **Minima d’ensembles vides.** Une fixture B antérieur à A a révélé que `arrayMin` sur les dates observées non nullables d’un tableau vide produisait une valeur par défaut. `arrayReduce('minOrNull', ...)` empêche cette fausse atteinte. La fixture T60 conserve le cas sans B postérieur et les retours multiples.
5. **Encodage des commandes.** Le runner fixe UTF-8 pour les sorties du sous-processus dbt. Une différence de test contenant une flèche Unicode avait provoqué une erreur d’affichage avec l’encodage Windows par défaut ; le résultat de test en échec n’a pas été transformé en succès.
6. **Clé de mois hors calendrier.** La lecture réelle `select month_date,month_date_key from dtm_revenue.fct_subscription_month_end order by month_date limit 1` a levé l’erreur ClickHouse 349 `CANNOT_INSERT_NULL_IN_ORDINARY_COLUMN`. Le calendrier prescrit commence au dernier jour du mois précédant les premières dates métier ; le premier jour de ce mois peut donc manquer. Le contrat de la seule colonne `fct_subscription_month_end.month_date_key` passe de UInt32 à Nullable(UInt32), conformément à la règle commune déjà écrite dans la fiche (date conservée, clé NULL si hors calendrier). Aucun historique ni calendrier fictif n’est ajouté. Le catalogue, le YAML et la vue sont alignés ; une fixture dédiée et la lecture forcée de toutes les colonnes contrôlent cette correction.
7. **Échelle des décimaux dans les empreintes.** La lecture réelle `toString(toDecimal128(1,4))` retourne `1`, alors que le contrat canonique impose `1.0000`. `toDecimalString(valeur, échelle_déclarée)` a été vérifié puis utilisé pour les empreintes décimales. Un test compare l’empreinte produite à sa préimage explicite. Les candidats écrits avant cette correction ne sont pas publiés ; leur code/règle et leurs données restent conservés.
8. **Couverture des montants par société.** Le contrôle global compte aussi les lignes/mois non rattachables à une société dont l’activité est inconnue ou active. Ces lacunes ne sont pas exclues du bilan sous prétexte que la DTR de grain société ne peut pas leur attribuer une identité. En présence de ces lignes, la disponibilité financière historique est partielle, et les effectifs certifiables restent NULL ; les compteurs diagnostiques sont conservés dans le JSON de qualité. Cela conserve les lacunes individuelles de D16 sans réintroduire un blocage de devise, qui est bien EUR par hypothèse de case.

Les schémas de sources ne sont substituables que pour les fixtures explicites. Les scénarios d’écriture utilisent des bases analytiques `stg_validation_*` et des cibles suffixées `_validation_*`. Les sources du case demeurent en lecture seule. Les révisions et les objets de validation sont conservés pour diagnostic ; aucune purge automatique n’est ajoutée.

### Chargement technique par partitions de clé
Après trois rejets MEMORY_LIMIT_EXCEEDED, un modèle persistant peut être écrit en huit partitions déterministes cityHash64(record_key) modulo 8. Le filtre intervient après toutes les fenêtres et jointures métier et avant la sérialisation du payload. Chaque modèle est entièrement terminé avant ses descendants ; la recomposition totale reste obligatoire. Les échecs dbt natifs et leurs exit codes sont conservés, avec un reçu de complétion orchestrée distinct. Aucun plafond serveur ni historique n'est modifié.
Le parseur du catalogue utilise désormais aussi l'index pour les deux fiches techniques sans ligne Destination ; leurs destinations dwh_common et dtr_sales sont vérifiées statiquement comme celles des 71 autres relations.

La requête portfolio_month conditionne désormais les totaux globaux à la disponibilité complète du registre. Les lignes sans société résolue ne figurant pas au grain société-mois, une somme des seules sociétés résolues serait insuffisante. Les contributions détaillées restent consultables ; les totaux globaux non prouvés restent NULL avec revenue_coverage_status.

### Reprise ciblée de publication
Deux tentatives ont terminé les contrôles de schéma, mais ont subi MEMORY_LIMIT_EXCEEDED durant des lectures de métadonnées de dbt avant un test ou une compilation. Le script implementation/resume_publication.py réutilise les preuves de recomposition et contrats réussis, vérifie l’intégrité physique des 37 modèles acceptés, puis reprend uniquement les contrôles de publication restants. Il emploie --no-populate-cache, sans modifier le plafond mémoire serveur ni le code des transformations accepté. La publication reste conditionnée à un JSON qualité valide et à des lectures identiques aux DTR du candidat.

### Consolidation des preuves après publication
La consolidation des journaux a révélé qu’une reprise dbt sélectionnait le suffixe hash d’un test générique, au lieu de son nom. Le grain concerné était déjà couvert par la comparaison intégrale des 37 recompositions et par le contrôle d’intégrité ; le test natif concerné est exécuté isolément pour compléter sa preuve. Le sélecteur de reprise est corrigé pour utiliser le nom du nœud dans le manifeste. Aucun modèle SQL ni donnée publiée n’a changé.
Le rapport exclut les artefacts run_results périmés laissés par un échec de démarrage dbt et ne confond plus publish avec published_tests. Les scripts runtime/report ont été corrigés après la publication : l’empreinte de code enregistrée reste celle du candidat effectivement construit. Une future construction avec ces scripts produira une nouvelle empreinte ; aucune métadonnée du run publié n’est réécrite.
